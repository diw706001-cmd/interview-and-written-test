# 笔试题目分析报告

## 《全栈开发工程师：HR 动态表单与通用接口引擎》

> 分析对象：`笔试题目8.20版本(1).pdf`（Obsidian 导出，共 3 页）

---

## 一、试卷整体解读

这是一道**大型全栈系统设计题（开放性综合题）**，不是传统选择/填空/算法题。它模拟真实企业需求：让 HR 能**零开发**地配置不同部门/岗位的入职表单，并自动获得对应的数据提交、查询、校验 API。

**硬性约束**
- 禁用 Java（前后端都算）
- 前端建议 React / Vue 3 / Svelte（仅为建议）
- 必须部署到云端（题目方提供 AWS 云服务器，需提供 SSH 公钥）
- 交付物 = 仓库地址 + 在线系统访问地址

**考察能力维度**
1. 动态 `JSON Schema` 设计能力（含嵌套、废弃、版本化）
2. 前端 Schema 驱动的动态渲染引擎（表单状态、联动规则、防死循环）
3. Schema 版本生命周期治理（10k 历史数据共存）
4. 通用 CRUD/查询引擎（基于 JSON 字段的动态校验、分页筛选）
5. 文件上传安全（敏感证件类）
6. 扩展性设计（插件 / 钩子 / 事件机制）
7. 并发控制（乐观锁 / ETag）
8. 审计与合规（谁在何时改了什么）

## 二、整体架构建议

```
┌──────────────────────────── 前端 ────────────────────────────┐
│  Form Builder(配置端)          Candidate Portal(填写端)        │
│    编辑 Schema → 发布新版    Schema + formState + RuleEngine  │

└──────────────────────────────────────────────────────────────┘
                          │ HTTPS
┌──────────────────────────── 后端 ────────────────────────────┐
│  Schema Service            Generic Data API Engine           │
│  · schema registry(版本化)  · 提交/查询/筛选(JSONB 动态)       │
│  · 发布与版本管理            · 联动规则统一执行(与前端一致)     │
│  · 审计日志                   · 事件发布 → Hook 扩展           │
├──────────────┬──────────────┬────────────────────────────────┤
│ PostgreSQL   │  对象存储     │  MQ/事件(钉钉/PDF/同步第三方)   │
│ (JSONB+GIN)  │  S3/MinIO    │  (Redis Stream/Kafka/SQS)      │
│              │  预签名直传   │                                 │
└──────────────┴──────────────┴────────────────────────────────┘
```

**推荐技术选型（满足"禁 Java"）**

| 层 | 可选方案 | 理由 |
|---|---|---|
| 前端 | React + TypeScript | 生态好，动态表单有成熟组件底座 |
| 后端 | Node.js(NestJS) 或 Go(Gin/GoFrame) | NestJS 可前后端共享 TS 类型与校验；Go 更重性能 |
| 动态校验 | Zod / ajv（Node）；go-playground（Go）| Zod 可与前端共享同一份 Schema 校验 |
| 存储 | PostgreSQL + JSONB + GIN 索引 | 比 MongoDB 更便于后续按需加关系表/事务 |
| 文件 | 对象存储（AWS S3 或 MinIO）+ 预签名 URL | 大文件不进数据库 |
| 联动表达式 | 成熟规则引擎（如 json-logic / cel-go）| **禁止手写 eval**，防注入且易做依赖分析 |
| 钩子队列 | Redis Stream / SQS / RabbitMQ | 异步可靠执行 + 重试 |
| 部署 | Docker Compose 单机起步，README 给全流程 | 满足"上云可访问" |

## 三、场景一：动态表单 Schema 设计与前端渲染引擎

### Q0 · Schema 数据结构设计

**设计要求覆盖**：字段 `key/label/type(input/select/upload/repeater)`、校验规则（必填/正则/min/max/email）、嵌套 Object、嵌套 Array(repeater)、默认值、Schema Version、字段废弃但历史数据仍存在。

**设计要点（写进作答，是得分点）**
- 校验规则独立成 `rules` 对象，`type` 只描述控件类别，二者解耦，便于扩展新控件。
- 每个字段用稳定的 `key` 作为数据键；`label` 只是展示文案 → 改名 = 改 label，不破坏数据。
- 嵌套统一抽象为 `Object / Repeater` 两类容器，便于渲染器递归处理。
- `version` 放顶层并**强制存在**，作为一切版本管理的锚点。
- 字段级 `deprecated`（或 `status: "deprecated"`）：置灰/隐藏 + 说明文案，**历史提交数据仍可读取**，只是不允许新提交再写入。

### Q1 · 前端动态渲染引擎

**组件职责划分**
- `DynamicForm`：入口，接收 `schema` + `initialData` + `onSubmit`。
- `FieldRenderer`：按 `field.type` 分发到 `InputField/SelectField/UploadField/RepeaterField/ObjectField`。
- `useFormState`：管理树形 `formState`（支持嵌套对象/数组下标）、脏检查、提交态、服务端错误映射。

**重点支持项的实现思路**

| 要求 | 实现方案 |
|---|---|
| 动态添加/删除数据项 | Repeater 内部维护 `items: FieldState[]`，add = 按 `itemSchema` 生成空项；删除时回收 `dirty/error`；渲染 `key` 用稳定 id（不要用数组下标当 key） |
| 校验 | 提交/失焦时对 `formState` 执行与后端**同一份**校验逻辑（前后端共享 schema，避免规则不一致） |
| 字段级/表单级错误提示 | 错误对象 `{ fieldKey: [message] }`；表单级错误单独通道（如跨字段校验失败、提交失败） |
| Dirty State | 顶层 `dirty` + 每字段 `dirty` 标记，`isFormDirty()` 用于离开确认/保存按钮状态 |
| Loading State | `submitting/loadingSchema/uploading` 等状态，渲染时按钮 disabled + 骨架屏 |
| Server Validation Error | 后端返回 `{ errors: [{ field, message }] }`，直接 merge 进同一错误对象展示在对应字段下 |

**核心骨架（React + TS 伪代码）**

```tsx
function DynamicForm({ schema, initialData, onSubmit }: Props) {
  const { formState, setField, errors, dirty, submitting } =
    useFormState(schema, initialData);
  const rules = useMemo(() => compileRuleGraph(schema.rules ?? []), [schema]);

  return (
    <FormProvider value={{ schema, formState, errors }}>
      {schema.fields.map(f => (
        <FieldRenderer
          key={f.key}
          field={f}
          value={getPath(formState, f.key)}
          onChange={v => { setField(f.key, v); fireRules(rules, f.key, v); }}
          errors={errors[f.key]}
        />
      ))}
      {errors.__form && <FormError msg={errors.__form} />}
    </FormProvider>
  );
}
```

**Rule Engine 与"防无限循环"（进阶题眼，务必回答）**

- 规则 DSL 建议（与后端共享）：
```ts
type Rule = {
  id: string;
  when: { field: string; op: "eq" | "gt" | "lt" | ...; value: unknown };
  actions: Array<{
    type: "show" | "hide" | "required" | "optional" | "setValue"
         | "disable" | "enable" | "showMessage";
    target: string;            // 目标字段
    value?: unknown;
  }>;
};
```
  例：`isNewGrad=是 → 隐藏 prevCompany 且取消必填`；`expectedSalary > 30000 → 显示提示"需要 HRBP 特别审批"`。

- **防无限循环的三件套**（A 改 B、B 改 C、C 改 A 场景）：
  1. **依赖图预处理**：构建「规则触发边」有向图，可先用拓扑排序检测环，标记环内规则仅允许"收敛型"执行。
  2. **逐字段递归传播 + 访问集合**：字段 X 变化 → 队列化依赖 X 的规则 → 执行 action 改变 Y 时，先比较新旧值；**若 Y 值未实际变化则不再传播**（这是最有效的截断手段）。
  3. **执行深度/次数上限**（如最多传播 20 层），超出即报"规则配置循环"错误并终止。

```ts
function fireRules(ruleGraph, changedKey, changedValue, formState) {
  const visited = new Set([changedKey]);
  const queue = [{ key: changedKey, value: changedValue }];
  let depth = 0;
  while (queue.length && depth++ < MAX_DEPTH) {
    const { key, value } = queue.shift();
    for (const rule of ruleGraph.byField.get(key) ?? []) {
      if (!evalWhen(rule.when, formState)) continue;
      for (const act of rule.actions) {
        const next = applyAction(act, formState);
        if (!deepEqual(getPath(formState, act.target), next)) {   // 值没变→不再传播
          setPath(formState, act.target, next);
          queue.push({ key: act.target, value: next });
        }
      }
    }
  }
  if (depth >= MAX_DEPTH) reportLoopError();
}
```

### Q2 · Schema 生命周期与版本管理

题目场景：当前 v3，已有 10,000 条历史提交。HR 修改：`employeeName→fullName`、删除 `nickname`、新增必填 `department`。

**方案：不可变发布 + 版本指针 + 提交快照**

1. **已发布 Schema 不允许直接改**（数据库层面约束）：
```
schemas 表：
  id, form_id, version, schema_json, status(draft/published),
  created_by, published_at, UNIQUE(form_id, version)
```
   任何修改 = 复制当前 published 生成新 draft → 改完 `publish` 升为 v4。发布用乐观锁（见 Q5）。

2. **历史 Submission 保留原 Schema Version**：
```
submissions 表：
  id, form_id, schema_version, data(JSONB), created_by, created_at
```
   - 历史 1 万条仍标记 `schema_version=3`，读取/导出时用 v3 渲染，保证原字段语义不漂移。
   - 三种迁移策略按需选择：
     - **读时映射（推荐）**：展示层维护 `renameMap`（`fullName←employeeName`），历史记录读取时透明映射，**不物理改动** 1 万条数据；
     - 物理回填：后台任务把 `data->>'employeeName'` 复制到 `data->>'fullName'`（一次性、可审计）；
     - 两者都做：物理复制 + 保留旧键。

3. **被删字段 nickname**：历史数据保留在 JSONB 中不回删；仅在新版本渲染中隐藏；`GET` 返回时提供 `includeLegacy` 选项。

4. **新增必填字段 department**：
   - 只对**新提交（v4+）**生效；历史记录不做强制补录。
   - 后台提供"批量补录/按人补填"入口（HR 可筛选缺 department 的候选人），避免线上展示缺字段报错。

5. **设计原则一句话总结**：*Schema 与数据都版本化；数据绑定它写入时的 Schema；Schema 变更只影响未来写入，对历史数据采用"读时兼容"而非"暴力迁移"。*

## 四、场景二：可配置通用数据 API 引擎

### Q0 · 通用提交接口 `POST /api/v1/dynamic-data/:formId`

**处理流程**
1. 取 `formId` 的**最新 published schema**（404 若不存在/未发布）。
2. 通用校验引擎按 Schema 递归校验 payload：类型、必填、regex/email/min/max、嵌套 object、repeater 条数、上传字段引用存在性。
3. 失败 → `400`，返回结构化错误：
```json
{
  "code": "VALIDATION_FAILED",
  "errors": [
    { "field": "email", "message": "字段 email 格式不正确" },
    { "field": "workHistory[2].company", "message": "字段 company 为必填项" }
  ]
}
```
4. 通过 → 入库（绑定当前 `schema_version`）+ 写审计 + **发布 `submission.created` 事件**触发 Hook。

**安全/健壮性**
- payload 大小上限（如 1MB）、单字段长度上限；
- 按 `formId` 限流，防止把该接口当垃圾存储；
- `unknown field` 策略：默认忽略或拒绝（建议 `strict` 可配，防脏数据）。

**引擎核心（伪代码）**
```ts
async function submitDynamic(formId, payload, actor) {
  const schema = await schemaRepo.getPublished(formId);
  const errors = validateBySchema(schema, payload);   // 与前端共享同一 schema
  if (errors.length) throw new ValidationError(errors);
  const row = await submissions.create({
    form_id: formId,
    schema_version: schema.version,
    data: normalizeUploadRefs(payload),   // 只存对象存储引用
    created_by: actor.id,
  });
  await auditService.record("create", { formId, submissionId: row.id, actor });
  await eventBus.emit("submission.created", { formId, schema, submission: row, actor });
  return { id: row.id, schemaVersion: schema.version };
}
```

### Q1 · 通用查询与筛选 `GET /api/v1/dynamic-data/:formId`

支持分页 + JSON 字段动态筛选（如 `experience > 3`）。

**Filter 请求协议（推荐显式 JSON，避免 SQL 注入面）**
```
GET /api/v1/dynamic-data/tech_onboarding?page=1&pageSize=20&sort=-createdAt
&filter=[{"field":"experience","op":"gt","value":3},
         {"field":"department","op":"eq","value":"tech"}]
```

**存储层（PostgreSQL JSONB 示例）**
```sql
-- 建 GIN 索引
CREATE INDEX idx_submissions_data ON submissions USING GIN (data jsonb_path_ops);

-- 筛选：experience > 3（数值路径）
SELECT * FROM submissions
WHERE form_id = $1 AND (data->>'experience')::numeric > 3
ORDER BY created_at DESC
LIMIT $2 OFFSET $3;

-- 存在性/包含型条件可用 @>
SELECT * FROM submissions WHERE data @> '{"isNewGrad":"是"}';
```
实现要点：
- 把白名单 op 集映射到 SQL 片段（`gt→>`、`regex→~`、`in→= ANY`…），**只拼接固定模板 + 参数绑定，绝不拼接用户字符串**；
- 字段 key 需在 schema 中存在（白名单校验），否则 400；
- 返回体带 `total`（可 `COUNT` 或缓存）、`page/pageSize`。

### Q2 · 字段联动与高级表达式引擎

- 联动规则是**业务约束**，前端执行只为体验，后端必须**同样执行**，否则 API 可绕过 UI 提交非法数据。
- 建议：规则 DSL 存后端，前端 `GET schema` 时同包下发（一份定义两端执行）；为杜绝两端行为漂移，可在**后端以 Node 跑同一份 TS 规则函数**（NestJS 前后端共享包）。
- **不要用 `eval`/`new Function`** 求值用户规则 → 用 `json-logic` / `cel-go` / `expr-lang` 等安全表达式引擎。
- 联动在提交接口中的落地：服务端在「校验前」按规则计算派生字段状态（如 `expectedSalary>30000 → 触发 HRBP 审批标记`，写入 `approvalNeeded: true`），保证接口语义与表单一致。

### Q3 · 文件上传安全（身份证/合同/简历/银行卡等敏感文件）

**核心结论先行：大文件永不进 Submission JSON，只进对象存储；应用只管理引用与权限。**

1. **直传架构（预签名 URL / STS）**
   - 前端 → 自有后端 `POST /api/v1/uploads/presign`（带鉴权，返回 `{ uploadUrl, objectKey, expiresIn }`）
   - 预签名 URL 限定：对象前缀（按 `formId/userId` 隔离）、最大大小、Content-Type 白名单 → 浏览器直传对象存储，应用服务器不经过大文件流量。
2. **后端在签发时校验**：登录态、上传配额、文件类型枚举（`pdf/doc/docx/xlsx/jpg/png` ≤10MB）。
3. **存储与回读安全**
   - 私有桶；对象 key 使用服务端生成随机 ID（`forms/{formId}/subs/{submissionId}/{uuid}.ext`），**绝不使用用户原始文件名**（防路径穿越/重名覆盖/XSS 型文件名）；
   - 敏感文件下载用**短期预签名 URL**，按角色鉴权；不可公开 CDN；
   - 所有上传写入审计（谁、何时、传了什么、大小）。
4. **内容安全校验**
   - 双重校验：`Content-Type` + **Magic Bytes 嗅探**（如 `%PDF`、`docx` 的 zip 头），防改扩展名伪装；
   - 拒绝 HTML/SVG（可嵌入脚本，XSS 风险）；图片不直接 `<img src=用户key>` 内联打开，预览用服务端代理或强制 `Content-Disposition: attachment`。
5. **Submission 里只存**：`{ objectKey, name, size, mime, uploadedAt }`（小元数据）。
6. 补充项：生命周期策略（离职 6 个月归档清理）、可选病毒扫描（S3 对象 lambda/ClamAV）、敏感数据脱敏展示。

### Q4 · 生命周期钩子与扩展机制

**设计：表单级「Hook 配置 + 事件总线」**
- 预定义事件：`submission.created / updated / status.changed`、`form.published`…
- 表单可配置启用哪些 Handler（如 tech_onboarding 启用 [dingtalkNotify, contractPdf, syncAttendance]）。

```ts
type HookContext = {
  formId: string;
  schemaVersion: number;
  submission: Submission;
  actor: User;
};

interface SubmissionHook {
  name: string;
  // 同步前置钩子：可拦截/补字段（返回错误则提交失败）
  beforeSubmit?(ctx): Promise<void>;
  // 异步后置钩子：通知/生成/同步
  afterSubmit?(ctx): Promise<void>;
}
```

**可靠性设计（重点）**
- 后置钩子一律**异步**（MQ/Redis Stream 消费），主接口只 `emit`，不被 PDF 生成/第三方同步拖慢；
- 每个 Handler 独立幂等键（`submission.id + hookName`），重试不产生重复钉钉通知/重复合同；
- 失败进重试 + 死信队列，监控告警；
- Handler 可插拔注册（SPI/依赖注入），新需求加一个类即可——这就是"无需开发介入"之外对研发侧的扩展承诺。

### Q5 · 并发修改（Form Builder 双人编辑）

**推荐：乐观锁 + 版本冲突处理。**
- `schemas` 表带 `version`（已是版本号，天然乐观锁字段）。
- HR A 读 v10 → A 保存：`UPDATE schemas SET schema_json=?, version=11 WHERE form_id=? AND version=10`；影响 0 行说明已被 B 改过 → 返回 **409 Conflict**。
- REST 语义：`GET` 响应头带 `ETag: "10"`，`PUT` 带 `If-Match: "10"`，不匹配返回 `412 Precondition Failed`。
- UI 冲突解决：拿到最新版后做 `diff`（`jsondiffpatch` 三向对比：A 的改动 vs B 的改动 vs 基线 v10）→ 给出"保留我的 / 采用最新 / 逐项合并"选择，避免静默覆盖。
- 可选增强：编辑期间对同一 form 加短暂写锁或"有人正在编辑"提示（Redis 占位 + 心跳），作为乐观锁的前置体验优化，但**以乐观锁为最终保障**。

### Q6 · 审计日志

**表结构**
```sql
CREATE TABLE audit_logs (
  id            BIGSERIAL PRIMARY KEY,
  form_id       TEXT NOT NULL,
  submission_id TEXT,
  actor_id      TEXT NOT NULL,          -- 谁
  action        TEXT NOT NULL,          -- create / update / delete / config_change
  field         TEXT,                   -- salary
  old_value     JSONB,                  -- 30000
  new_value     JSONB,                  -- 35000
  diff          JSONB,                  -- 字段级变更集
  meta          JSONB,                  -- ip / user_agent / reason
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_audit_form_time ON audit_logs (form_id, created_at DESC);
CREATE INDEX idx_audit_actor     ON audit_logs (actor_id, created_at DESC);
```

**实现方式**
- 通用引擎在**服务层统一 diff**（更新前读旧值、更新后算字段级 `diff`），比数据库 Trigger 更好控制"谁、为什么"；
- 管理端所有 Schema 配置变更也审计（`config_change`），满足"谁在什么时候改了什么表单"；
- 示例记录：`{ form_id: "tech_onboarding", actor: "hr_li", action: "update", field: "salary", old_value: 30000, new_value: 35000, created_at: ... }`；
- 查询接口按 `form_id / actor / action / 时间范围` 分页，敏感数据访问本身也记录；
- 保留策略（如 5 年）与导出合规。

## 五、工程交付与答题建议

**建议答题/实现顺序（也即工时分配）**
1. Schema 设计 + 校验引擎（前后端共享）——这是全题的地基；
2. 通用 API 引擎（提交 + 查询筛选 + 审计 + 乐观锁发布）；
3. 前端渲染引擎（核心表单渲染 + 状态/校验 + Rule Engine）；
4. Form Builder（编辑/发布/版本/diff）；
5. 文件直传（预签名）；
6. 钩子示例（钉钉通知 + PDF 合同生成，各一个即可演示）；
7. 部署 + README + 演示。

**Repo 结构建议**
```
repo/
├─ docs/            # 设计文档：Schema 协议、API 文档、规则 DSL
├─ packages/
│  ├─ shared/       # schema 类型 + 校验器 + 规则 DSL（前后端共用）
│  ├─ server/       # 通用数据 API + 钩子 + 审计
│  └─ web/          # 动态渲染引擎 + Form Builder
├─ migrations/      # 数据库迁移（含 GIN 索引）
└─ docker-compose.yml
```

**加分项（明确写进 README/答辩）**
- Zod/TS 全链路类型安全：Schema 定义即类型；
- 校验器、Rule Engine、版本迁移各写单测；
- OpenAPI 自动文档；错误码规范；
- 性能：分页用游标/键集分页替代 OFFSET 大数据场景；
- 演示数据：预置"技术岗/销售岗"两个表单展示配置→填写→查询闭环。

**常见扣分点（务必避免）**
- 每个表单手写路由/硬编码字段（违背题目本意）；
- `eval` 执行联动表达式；
- 校验失败只返回笼统 `400`，没有字段级 message；
- 文件 Binary 直接塞 DB/Submission JSON；
- 无版本管理 / 直接改已发布 schema / 历史数据无人处理；
- 钩子同步阻塞提交主流程、无重试；
- HR B 静默覆盖 HR A（无并发控制）；
- 不做任何审计。

## 六、结语

本题本质是让候选人**从零搭一个"低代码表单平台的最小闭环"**：Schema 驱动的前端渲染、通用的数据存取引擎、版本与并发治理、扩展与合规。建议把回答重心放在"**如何保证动态性、一致性与可扩展性**"上：动态 Schema 是一切数据协议的源头；前后端共享校验与规则是正确性底线；版本化+乐观锁+审计是工程成熟度证明。按上述框架实现即可覆盖所有小问并有余量冲击加分项。
